# Cindy 项目学习路线与可获取知识点

> 配套文档：`项目学习指南.md`（架构总览）、`项目学习指南.mindmap.html`（思维导图）。
> 本文给出一条**由浅入深、可对照源码**的学习路线，以及每个阶段能学到什么。
> 所有文件路径都是仓库内真实路径，可直接打开阅读。

## 一、学习前准备（0.5 天）

### 目标
把环境跑起来，建立「产品体感」，避免空读代码。

### 步骤
1. 读 `README.zh-CN.md`（产品定位）+ `AGENTS.md` 的「仓库边界」「通用工作流程」两节。
2. 读 `docs/dev-rules/repo-map.md`，建立目录心智模型。
3. 按 `CONTRIBUTING.md` 装：Node 22 + pnpm 10 + Git LFS → `pnpm install`。
4. 启动 dev：`pnpm restart:desktop:remote --region=global --isolated=study`（`--isolated`
   沙箱隔离数据，不污染正式版；首次需登录或「跳过登录」）。
5. 跑一遍核心交互：新建任务 → 与 Claude Code 对话 → 观察工具调用流 → 开启 Orca 协同
   派一个 Worker → 装/用一个插件。
6. 浏览 `docs/` 三类规则目录，**不需要全读**，知道触发时机即可。

### 能学到的知识点
- pnpm workspace monorepo 的依赖拓扑与 `pnpm --filter` 用法。
- Electron 应用的本地启动差异（dev vs packaged、userData 隔离、CDP 调试端口）。
- 区域化（`cn`/`global`）构建身份如何影响端点与数据目录。

## 二、第一阶段：Electron 应用骨架（1–2 天）

### 目标
理解「Renderer 不可信 → preload 最小桥 → Main 特权」三层信任模型与 IPC 授权边界。

### 阅读顺序
1. **入口链**：
   - `apps/desktop/src/main/index.ts`（顶部注释讲清了 region userData 隔离、happy-eyeballs
     超时等真实坑）→ 注释指向 `bootstrap-electron.ts`（动态 import 的唯一例外）。
   - `apps/desktop/src/renderer/index.tsx`（i18n 同步 init 防首屏闪烁、TapDB 初始化时机）。
2. **preload 桥**：`apps/desktop/src/preload/preload.ts`，对比 `ghostPreload.ts`（插件用）。
   - 观察它如何只暴露固定方法、剥离 `IpcRendererEvent`、不暴露 `ipcRenderer.on/send/invoke`。
3. **Vite 多配置**：`apps/desktop/vite.*.config.ts` 有 10 个配置——main、renderer、preload、
   ghost-preload、db-worker、silk-worker、watcher-host 等。理解 Electron 工程为何要为
   不同进程/worker 各出一份 Vite 配置。
4. **打包**：`apps/desktop/forge.config.ts` + `package.json` 的 maker-squirrel/deb/nsis。
5. **安全规则**：`docs/dev-rules/electron-security-and-process-boundaries.md` 全文。
6. **安全代码**：
   - `apps/desktop/src/main/security/csp.ts`（CSP 统一注入）。
   - `apps/desktop/src/main/webview-security.ts`（`will-attach-webview` hardener）。
   - `apps/desktop/src/main/renderer-boot-guard.ts`。

### 动手练习
- 用 grep 找一个 IPC handler（如 `apps/desktop/src/main/maker-ipc/` 下任意 `*.ts`），追踪：
  它如何验证 `event.senderFrame`？payload 如何校验？错误如何用统一协议返回？
- 找一个 BrowserWindow 创建处，核对是否满足 sandbox/contextIsolation/nodeIntegration:false。

### 能学到的知识点
- **Electron 安全模型**：sandbox、contextIsolation、nodeIntegration、webSecurity、Fuses、CSP。
- **IPC 作为授权边界**：sender 校验、payload 校验、资源归属校验、fail-closed。
- **preload contextBridge 最小暴露面**设计与反模式。
- **多进程 Vite 打包**：main/preload/renderer/worker 各自的构建约束。
- **动态 import 禁令**为什么（打包/加载时机/错误路径的不确定性）。
- **区域化数据隔离**：同机双装 cn/global 如何靠 userData 目录天然分库。
- **真实工程坑**：happy-eyeballs 250ms 默认超时在 VPN 下的 `fetch failed`、TapDB 设备 ID
  按 origin+userData 分家导致 dev 造出大量「虚拟设备」。

## 三、第二阶段：本地数据与布局系统（1 天）

### 目标
理解 SQLite + drizzle 的多账号迁移体系，以及「布局树作为用户级配置」的设计。

### 阅读顺序
1. **schema 与 migration**：
   - `apps/desktop/src/main/localDb/schema.ts`（`sessions`、`messages`、`orca_teams`、
     `orca_workers`、`daily_spend` 等表）。
   - `apps/desktop/drizzle/*.sql`（90 个 migration，按编号看演进）。
   - `apps/desktop/src/main/localDb/migrate.ts` + `migrationRunner.ts`。
   - 规则：`docs/dev-rules/database-and-migrations.md` +
     `multi-account-database-architecture.md`。
2. **布局树**：
   - `apps/desktop/src/shared/layoutTree.ts`（**零依赖纯函数**，必读——immutable、损坏输入
     永不抛异常、`coerceLayout` 兜底）。
   - `apps/desktop/src/main/layout/LayoutStore.ts`（持久化 + 校验/回退）。
   - `apps/desktop/src/renderer/panels/registry.ts` + `builtinPanels.tsx`（面板注册）。
   - 规则：`docs/dev-rules/architecture-invariants.md` §3。

### 动手练习
- 在 `--isolated=study` 沙箱里加一条测试 migration，观察「未合入 migration 必须在沙箱跑」
  的护栏如何工作。
- 读 `layoutTree.ts` 的 `coerceLayout` 与份额比较容差（`FRACTION_TOLERANCE`），理解它如何
  用纯函数避免 renderer/main 两份校验漂移。

### 能学到的知识点
- **drizzle-orm + better-sqlite3** 的 schema 定义与迁移工作流。
- **迁移不可变性与向后兼容**：历史 migration 不手改、用 forward-only 增量。
- **多账号数据库架构**与「沙箱隔离」工程实践。
- **纯函数数据模型 + 双进程共用校验**的防漂移设计。
- **递归数据结构（split/pane 树）的合法性不变量**：唯一性、可见性、最小宽度、位置记忆。
- **防御性编程**：浮点容差、深度上限、字符串长度上限，防损坏/恶意存档爆栈。

## 四、第三阶段：maker-core —— Agent 编排核心（3–5 天，重点）

### 目标
这是 Cindy 最有学习价值的部分：如何用代码（而非 prompt）保证多套异构 Agent Harness 的
行为可控、可缓存、可观测。

### 阅读顺序
1. **先读规则**：`docs/dev-rules/maker-core-and-agent-behavior.md` 全文（四项指标 + system
   prompt 门禁）。
2. **类型层**：`packages/maker-core/src/types/events.ts`（`AgentEvent` union —— 让 UI 能
   通用消费两套 vendor 事件的核心抽象）。逐个理解 17 种事件类型语义，尤其是
   `error.isTerminal`/`willRetry` 的兜底优先级。
3. **BaseAgent 抽象**：`packages/maker-core/src/agents/base-agent.ts`（1769 行，分多次读）。
   - 1448 行起的 `abstract class BaseAgent`：`abstract kind`、`abstract capabilities`、
     `abstract startSession`。
   - 理解「不支持的能力默认抛 `NotSupportedError`，子类按 capabilities 覆盖」的模板方法。
4. **Claude Code 实现**：
   - `agents/claude-code/index.ts`（6257 行，最重）——重点看 system prompt 多段拼接顺序
     （SDK preset → `MAKER_SYSTEM_PROMPT_APPEND` → memoryRules → contactsRules →
     host runtimeConfig → MEMORY.md 快照 → per-call userPrompt）。
   - `agents/claude-code/translator.ts`（1861 行）——vendor SDK 事件 → `AgentEvent` 的归一化，
     **热路径**，观察它如何无丢失无错序映射。
   - `agents/claude-code/system-prompt-append.md` + `system-prompt-append.ts`（宪法层文本）。
   - `agents/claude-code/local-process-spawn.ts`（CLI 进程拉起）。
   - `agents/claude-code/fork-jsonl-repair.ts`（fork 后 JSONL 修复，真实坑）。
5. **Session 注册中心**：`packages/maker-core/src/maker.ts`（1058 行）——按 `(agentKind,
   workDir)` 创建 Session，预留 MetaAgent 升级（关键方法 protected）。
6. **usage-tracker**：`packages/maker-core/src/agents/shared/usage-tracker.ts`——token/缓存率
   计量，理解 prompt cache 命中如何依赖前缀逐字节稳定。
7. **测试**：`agents/claude-code/__tests__/` 下 27 个测试，挑 `translator-*.test.ts`、
   `fork-jsonl-repair.test.ts`、`invalid-resume-recovery.test.ts` 读，看真实回归点。

### 动手练习
- 在 `--isolated` 沙箱里跑一个 turn，用 `/context` 或 usage-tracker 观察缓存命中率。
- 故意在 system prompt 稳定段塞一个时间戳（**不要提交**），观察缓存率下降——体感理解
  前缀稳定性。
- 读 `translator.ts` 找一个 vendor 事件，画出它映射到哪种 `AgentEvent`，验证「无丢失无错序」。

### 能学到的知识点
- **Template Method + 能力声明（capabilities）** 的抽象设计：统一接口面 + 差异下沉子类。
- **Adapter/Translator 模式**：把异构 SDK 事件流归一化进统一 union type，让 UI 通用消费。
- **流式事件循环（AsyncQueue）的非阻塞模型**：先入队、消费端 async 流式吐，热路径禁阻塞。
- **LLM prompt cache 的工程化守护**：前缀逐字节稳定、拼接顺序固化、易变内容隔离到 per-call。
- **「代码优先于 prompt」的确定性原则**：校验/状态机/流程编排/权限/重试用代码，不甩给模型。
- **model 路由禁裸别名**：避免二进制升级后别名漂到下一代模型，用户选的与实际命中的不一致。
- **Agent SDK 集成的真实坑**：fork JSONL 修复、invalid resume 恢复、auto-continued turn
  in-flight、abort 停后台任务。
- **测试驱动的不变量守护**：translator 事件流、context window、empty response、silent stop。
- **「宪法层」改动门禁**：system prompt 改动需 owner 确认 + 实测评估的工程治理。

## 五、第四阶段：Orca 多 Agent 协同（2–3 天）

### 目标
理解一个生产级多 agent 协同系统的状态机、竞态处理与越权防御。

### 阅读顺序
1. **先读规则**：`docs/dev-rules/orca-team-architecture.md` 全文（Part 1 当前实现 + 坑点）。
2. **数据模型**：`apps/desktop/src/main/localDb/schema.ts` 的 `sessions.orcaRole`、
   `orcaTeams`、`orcaWorkers`（注意 partial unique 约束：active team 唯一、focused worker 唯一）。
3. **四个 service**（`apps/desktop/src/main/maker-ipc/orca*.ts`）：
   - `orcaLifecycleService.ts`（start/enable team、首个 worker 补偿）。
   - `orcaWorkerCreationService.ts`（创建校验、权限偏好）。
   - `orcaTeamService.ts`（派活/resume/idle/archive/auto-bridge/`rollbackAcceptedDispatchState`）。
   - `orcaInterAgentDispatcher.ts`（Lead↔Worker 消息直发/排队/accepted callback）。
4. **MCP 控制面**：`packages/lizi-mcps/src/orca/server.ts`（16 工具顶层注册 +
   `DirectToolSink`）+ `packages/orca-workflow/src/orca-bridge-prompt.ts`（Lead/Worker prompt）。
5. **Codex 路由**：`apps/desktop/src/main/mcp-integrations/codexHttpBridge.ts` +
   `codexMcpThreadContextStore.ts`（`params._meta.threadId` fail-closed 路由）。
6. **UI**：`apps/desktop/src/renderer/features/cc-agent/OrcaSplitView.tsx`、`OrcaWorkerPanel.tsx`、
   右侧栏 `plugins/orca-workers`、`lib/orcaSessionIdentity.ts`。
7. **测试矩阵**：`orca-team-architecture.md` 末尾的「重启矩阵」5 个场景对应的测试。

### 动手练习
- 追踪一次 `send_to_worker` 的完整链路：MCP 调用 → context 路由 → 归属校验 →
  `dispatchOrEnqueueOrcaInterAgentMessage` → accepted callback → `running` 状态广播 →
  terminal turn → auto-bridge 回传 Lead。
- 找 `rollbackAcceptedDispatchState`，理解「派活 accepted 后失败，只回滚仍 running 的 worker，
  不覆盖已 done/error/idle 的终态」。
- 找 `resolveWorkerRef`，理解「同时接受 worker_id/session_id，但只在 caller 自己的 worker
  列表内解析」的纵深防御。

### 能学到的知识点
- **多 agent 协同的状态机设计**：Lead/Worker/Team 三表模型 + partial unique 约束保证不变量。
- **竞态与一致性**：CAS 原子写、active dispatch 计数、transition 串行队列、`closeIfIdle` 互斥。
- **消息可靠性**：忙碌目标不丢消息（入队而非失败）、queued accepted 同样结算、手动中断不
  auto-bridge。
- **越权纵深防御**：工具可见性≠权限边界、context 路由 fail-closed、caller 归属校验正交。
- **MCP 工具与 IPC 共用 service**保证权限/状态/回滚语义一致。
- **无损资源回收（idle hibernate）**：释放 runtime 但保留记录/历史/上下文，CAS 标记 `idle_since`。
- **「执行通道披露」**：Lead 验收必须按同一通道确认真实终态，禁用原生 subagent 冒充 Worker。
- **重启恢复的鲁棒性**：内存态丢失后从 DB 懒合成 vendorOptions/worker link，5 种重启场景矩阵。

## 六、第五阶段：插件系统与沙箱（2 天）

### 目标
理解 Electron 沙箱进程隔离、能力 slot 权限模型、存量兼容红线。

### 阅读顺序
1. **先读规则**：`docs/dev-rules/plugin-security-and-authoring.md` 全文。
2. **身份卡**：`apps/desktop/src/shared/ghost.ts`（`validateGhostManifest`、管子协议类型）。
3. **运行时**：`apps/desktop/src/main/cindy-brain/runtime/GhostRuntime.ts` +
   `GhostManager.ts` + `electronSandboxAdapter.ts`（独立沙箱进程 + 专属 session partition）。
4. **能力 slot**（`apps/desktop/src/main/cindy-brain/*Slot.ts`）：挑 `networkSlot.ts`、
   `skillSlot.ts`、`fsSlot.ts`、`errandSlot.ts` 精读。
   - `networkSlot.ts`：白名单域名 + 凭证主机注入无明文读回。
   - `skillSlot.ts`：唯一越出沙箱的能力，`checkSkillMdConsistency` + `reconcileGhostSkillLinks`。
   - `fsSlot.ts`：grant/deposit/ledger 资源交接。
   - `errandSlot.ts`：派活取件，权限档 plan/acceptEdits/auto，**bypassPermissions 协议层不存在**。
5. **编写手册**：`apps/desktop/src/main/cindy-brain/forge.ts` 的 `FORGE_GUIDE`。
6. **面板窗口**：`apps/desktop/src/main/ghost-panel-window/window.ts`（专属 partition、零通用 preload）。
7. **ghost 总机**：`packages/cindy-tools/src/ghost/`（`ghost_list`/`ghost_info`/`ghost_call`）。

### 动手练习
- 找一个 `*.cindy` 插件包，对照 `ghost.json` 与各 slot 声明，理解「manifest 声明 → 注入确认框
  逐项展示 → host 强制授权」链路。
- 追踪一次 `skill` 槽的链接对账：`reconcileGhostSkillLinks` 如何只增删安装根内的 symlink/junction。

### 能学到的知识点
- **Electron 沙箱进程隔离**：独立进程 + 专属 partition + webContents 反查身份。
- **能力 slot 权限模型**：声明 → 校验 → 确认 → host 强制，prompt 不构成边界。
- **凭证安全**：主机保险库注入、无明文读回、`gh-cli`/`oidc-token` 等 source 的边界。
- **资源交接的 grant/deposit/ledger 模式**：不暴露宿主绝对路径给沙箱。
- **越出沙箱能力的安全边界**：声明一致性 + 链接对账（skill 槽）。
- **存量兼容红线**：向下兼容、不要求重装/重确认/重配置、自动迁移、白名单确认门。
- **AI 代办通道的固定边界**：快问快答 vs 派活取件，任务文本只进 user 消息不进 system prompt。

## 七、第六阶段：跨端协议与模型桥接（1–2 天）

### 目标
理解跨设备远程控制的协议分层与「让 Claude SDK 访问非 Anthropic 后端」的桥接链路。

### 阅读顺序
1. **device-link**：`packages/device-link/src/protocol.ts`（envelope）+ `allowlist.ts`
   （deny-by-default）+ `transport.ts`（重连/心跳）+ `client.ts`。
   - 规则：`docs/dev-rules/protocol-compatibility.md` + `remote-and-mobile-adaptation.md`。
2. **模型桥接**：
   - `packages/model-providers/`（供应商目录 + 路由抽象）。
   - `packages/anthropic-compat-proxy/`（本地回环代理，剥离专有字段）。
   - `packages/anthropic-responses-bridge/`（Anthropic Messages ↔ OpenAI Responses 转换）。
   - `packages/responses-anthropic-bridge/`（反向桥 + SSE 回译）。
   - 桥接代码：`apps/desktop/src/main/maker-host/codex-gateway-config.ts` +
     `codex-proxy-host.ts`（`cindy_gateway` vs `cindy_openai` 两条通道）。

### 能学到的知识点
- **跨设备 wire protocol 设计**：envelope、allowlist、重连/心跳、被控端为真相源。
- **deny-by-default 白名单方向**（不得改成黑名单）的隐私意义。
- **协议适配层（compat proxy）**：剥离专有字段让 SDK 访问异构后端。
- **双向协议桥**：Messages API ↔ Responses API 的请求/图片/工具/thinking 转换 + SSE 回译。
- **多投递通道的唯一性约束**：每 thread 只选一个 instructions 投递来源，禁同时走两条。

## 十、建议的时间投入与顺序

| 阶段 | 主题 | 建议时长 | 优先级 |
|---|---|---|---|
| 0 | 环境与产品体感 | 0.5 天 | 必做 |
| 1 | Electron 骨架与安全 | 1–2 天 | 必做 |
| 2 | 数据库与布局 | 1 天 | 必做 |
| 3 | maker-core Agent 编排 | 3–5 天 | **最高** |
| 4 | Orca 多 agent 协同 | 2–3 天 | 高 |
| 5 | 插件沙箱 | 2 天 | 高 |
| 6 | 跨端协议与模型桥接 | 1–2 天 | 中 |
| 7 | 工程规范与门禁 | 1 天 | 中 |

**最短路径**（时间紧只看核心）：阶段 0 → 1（安全模型）→ 3（maker-core）→ 4（Orca）。
这四块是 Cindy 区别于普通 Electron 应用的核心竞争力，也是最能迁移到其它 Agent 产品的
知识。

**配套验证**：每读完一个阶段，回到 `docs/项目学习指南.mindmap.html` 折叠对应分支，用
自己的话复述一遍——能讲清就是真懂了。
