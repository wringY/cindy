# Cindy 项目学习指南

> 本文是为快速了解 Cindy 客户端仓库而整理的架构与工程导读。事实源是代码与
> `docs/dev-rules/`、`docs/product-rules/` 下的权威规则文档；本文冲突时以代码与
> 权威规则为准。

## 1. 项目是什么

Cindy 是一个**开源、开箱即用的 AI Agent 客户端**，运行在用户自己的电脑上，使用本地
文件和已登录的应用替用户把真实工作做完。核心定位：

- **连接而非重造智能**：首批兼容 **Claude Code** 与 **Codex** 两套 Agent Harness，
  自研 Harness（Pi）也在接入；模型与 Harness 可自由组合、同一任务中随时切换。
- **一个任务可由多个 Harness × 模型组合的 agent 规划、并行执行、独立 review**
  （Orca 多 Agent 协同）。
- **可培养**：Memory（记忆）、Skill（技能）、Automation（定时任务）、MCP（系统接入）、
  Plugin（插件改功能/界面）、Source（Apache-2.0 可 fork）。
- 能操作浏览器、电脑和手机，支持从 IM 和定时任务派活。

本仓库是 **Cindy 客户端 monorepo**（桌面端 + 手机端 + 共享 packages），**服务端在独立
仓库**。客户端本身免费，模型供给支持：官方登录按量扣减、一键复用已有 Claude Code /
Codex 订阅、或接自己的 API key / 本地模型。

**双区域**：`cn`（中国大陆版，cindy.cn）与 `global`（国际版，cindy.app）。未显式指定
区域一律落在 `global`，只标注中国大陆版。

## 2. 技术栈与开发工具

### 2.6 工程脚本与门禁（`scripts/`，45 个）

仓库有大量自动化 guard，体现「用代码保证确定性」的工程哲学：

- `ensure-deps.mjs` / `ensure-agent-binaries.mjs` / `ensure-dev-runtime-assets.mjs`：依赖
  与运行时资产就绪检查。
- `check-dco.mjs` / `install-dco-hook.mjs`：DCO 签名门禁。
- `check-i18n.mjs` / `check-i18n-glossary.mjs`：i18n 完整性与术语表（`i18n/GLOSSARY.md`）
  裁决一致性。
- `check-endpoint-literals.mjs`：端点清单字面量校验（防硬编码 URL）。
- `brand-terminology-guard.mjs`：产品术语门禁。
- `hardcoded-color-audit.mjs` + `hardcoded-color-exemptions.json`：禁止硬编码颜色，
  强制走语义 token（双模式交付门槛）。
- `scheduler-ci-guard.mjs` / `test-gate-lock.mjs` / `test-workspaces.mjs`：分层测试
  （git-integration / db / migration 等多 tier）。
- `check-pr-design-basis.mjs` / `check-pr-template-rules.mjs`：PR 模板与设计依据校验。

### 2.7 开发入口

```bash
# Agent 启动 Desktop 必须用 restart 包装命令，并显式选区域
pnpm restart:desktop:remote --region=cn      # 中国大陆版
pnpm restart:desktop:remote --region=global  # 国际版
```

关键参数：`--isolated[=<名字>]`（独立 userData 沙箱，跑未合入 migration 时必用）、
`--passive`（让出定时任务调度，多开共享 userData 时用）、`--preserve-running`（并行
dev 不停旧实例）。TapDB 统计在 dev 构建默认不上报（`isReportingBuild()` 门控）。

## 3. 顶层架构

### 3.1 进程与信任边界（Electron）

Cindy 把 Electron 三进程模型当作**信任边界**来设计（见
`docs/dev-rules/electron-security-and-process-boundaries.md`）：

```
┌──────────────────────────────────────────────────────────┐
│ Renderer（不可信 UI）                                     │
│  - 不 import electron/node:*，不读写磁盘/DB/凭证          │
│  - React UI、展示状态、纯 UI 校验                          │
│  - XSS 不能因此获得 Node/IPC 能力                          │
└───────────────▲ contextBridge（最小方法）──────────────────┘
                │ IPC（授权边界）
┌───────────────┴──────────────────────────────────────────┐
│ Preload（最小权限桥）                                     │
│  - 只暴露按用途命名的固定方法，剥离 IpcRendererEvent      │
│  - 不暴露 ipcRenderer.on/send/invoke 原语                 │
└───────────────▲──────────────────────────────────────────┘
                │
┌───────────────┴──────────────────────────────────────────┐
│ Main（特权边界）                                          │
│  - 系统API、持久化、网络凭证、文件、进程管理、权限裁决     │
│  - 禁止运行时动态 import()，依赖一律顶层静态 import        │
│  - IPC handler 验证 sender/payload/归属/权限              │
└──────────────────────────────────────────────────────────┘
```

要点：

- BrowserWindow 强制 `sandbox/contextIsolation/webSecurity: true`，`nodeIntegration: false`。
- `webview-security.ts` 在 `will-attach-webview` 阶段覆盖 Renderer 传入的全部安全选项
  （hardener 挂 `web-contents-created`，全局生效）。
- CSP 由 `main/security/csp.ts` 统一注入；正式包不新增远程脚本/`'unsafe-inline'`。
- 打包保留 Electron Fuses：关闭 RunAsNode/Node options/CLI inspect，开启 cookie 加密、
  ASAR 完整性校验。

### 3.2 三层代码职责

| 层 | 职责 | 约束 |
|---|---|---|
| `renderer/` | 组件渲染、交互状态、展示编排 | 无特权，不持长期业务真相 |
| `main/` | Electron 生命周期、IPC 授权、OS 集成、持久化、特权副作用 | 静态依赖、fail-closed |
| `shared/` | 跨进程协议、类型、常量、纯函数 | 零 IO、零副作用 |
| `packages/*` | 可复用领域逻辑 | 通过接口注入宿主能力，**不 import renderer，不反向 import Main** |

### 3.3 主界面布局树

布局真身是 `apps/desktop/src/shared/layoutTree.ts` 定义、`main/layout/LayoutStore.ts`
持久化的**全局递归 split/pane 树**（零依赖纯函数，renderer 与 main 共用同一套校验）。

核心不变量：

- 面板身份只认 `panelKind`，**禁止用「左栏/右栏」等当前位置充当业务身份**。
- `chat-main` 在整棵树中**恰好一个、始终可见、不可关闭、不可折叠**，最小宽 400px。
- 布局是**用户级配置**而非 session 数据，启动随首帧同步就位，禁止先画默认再跳成用户布局。
- 未知 `panelKind` 保留在存档但不渲染，重新注入后原位恢复（位置记忆）。

### 3.4 本地数据库

- better-sqlite3 + drizzle-orm，schema 在 `apps/desktop/src/main/localDb/schema.ts`。
- **90 个 migration**（`apps/desktop/drizzle/*.sql`），走 `migrationRunner.ts`。
- 多账号架构（`multi-account-database-architecture.md`），数据库迁移有严格的「未合入
  migration 必须在 `--isolated` 沙箱跑」规则。
- 历史 migration **不可手改**；schema 注释滞后属文档 bug，要走正常 review 流程。

## 4. 核心子系统

### 4.1 maker-core：Agent 编排核心（最重要）

`packages/maker-core` 是所有 Agent 会话的事件流与 prompt 组装中枢，**零 Electron 依赖**。
约 219 个 TS 文件、13 万行。设计原则见 `maker-core-and-agent-behavior.md`。

#### 设计模式

1. **Template Method（BaseAgent 抽象）**
   - `src/agents/base-agent.ts` 定义统一抽象，对齐 vendor `VendorSession` 接口面。
   - 不支持的能力默认抛 `NotSupportedError`，子类按 `capabilities` 覆盖。
   - 共用逻辑下沉到 BaseAgent，子类只实现差异部分，避免每个 Agent 各写一套编排。

2. **Translator 模式（vendor 事件归一化）**
   - 每个 agent 有 `translator.ts`，把 vendor SDK 事件**无丢失、无错序**映射进统一的
     `AgentEvent` union（`text`/`thinking`/`tool_use`/`tool_result` 等）。
   - translator 是**每事件/每 token 都过一遍的热路径**，禁止同步阻塞调用。

3. **AsyncQueue 事件循环**
   - 「先入队、消费端 async 流式吐」的非阻塞模型；`handle.send` 路径不加额外网络往返。

4. **Session 注册中心 + Agent 路由（`maker.ts`）**
   - 持有按 `AgentKind` 注册的 BaseAgent 实例，按 `(agentKind, workDir)` 创建 Session。
   - 预留 MetaAgent 升级路径（自带 LLM 决策循环），关键方法 protected。

#### 三类 Agent 实现

| Agent | 目录 | 说明 |
|---|---|---|
| Claude Code | `src/agents/claude-code/` | 封装 Claude Agent SDK，system prompt 多段拼接，fork JSONL 修复，subagent 定义 |
| Codex | `src/agents/codex/` | 封装 Codex app-server，thread context 路由，Responses API 桥接 |
| Pi | `src/agents/pi/` | 自研 Harness（见 `pi-harness.md`） |

每个 agent 目录典型文件：`index.ts`（会话创建与 system prompt 拼接）、`translator.ts`
（事件映射）、`local-process-spawn.ts`（进程拉起）、`commands.ts`、`capability-routing.ts`。

#### 四项核心指标不变量（改动 maker-core 必须守护）

1. **缓存率（Anthropic prompt cache）**：请求前缀必须**逐字节稳定**。system prompt 按
   固定顺序拼接（SDK preset → `MAKER_SYSTEM_PROMPT_APPEND` → memoryRules → contactsRules
   → host runtimeConfig.systemPrompt → MEMORY.md 快照 → per-call userPrompt）。禁止把
   每轮变化的内容（时间戳、随机文案）塞进稳定前缀；禁止调整拼接顺序；禁止会话中途
   增删/重排 tool 定义或 MCP server。

2. **性能/返回速度**：热路径（event loop、translator）不塞同步阻塞、不深拷贝大对象、
   不加串行 await。

3. **返回内容准确性**：translator 不丢事件、不错序、不错配类型；model 路由**只用显式
   版本号，禁止 `'opus'`/`'sonnet'` 裸别名**（二进制升级后别名会漂到下一代模型）。

4. **review 前实测**：落在 prompt 组装/tool/MCP/translator/event loop/model 映射/usage
   计量路径的改动，PR 必须显式写明影响哪几个指标、用什么方法实测、结论如何。

#### 两条硬性原则

- **优先用代码保证确定性，而非依赖 prompt**：判断/分支/校验/状态机/流程编排/权限/重试
  一律用代码实现，不甩给 prompt「自己判断」。
- **system prompt 改动门禁**：任何人不得擅自修改 system prompt（`MAKER_SYSTEM_PROMPT_APPEND`
  等），必须先与仓库维护者讨论确认。system prompt 是产品行为与质量的「宪法层」。

### 4.2 Orca：多 Agent 协同

Orca 是 Cindy Desktop 内的多 agent 协同能力（见 `orca-team-architecture.md`）：

- **Lead session**（主线，`orca_role='lead'`）负责拆任务、派活、验收、汇总；
- 多个 **Worker session**（`orca_role='worker'` + `orca_workers`）并行/串行执行；
- Worker 是**完整会话**（有独立 agent/model/context/历史），不是一次性 subagent。

#### 控制面

- `cindy_orca` MCP server 顶层注册 **16 个工具**（13 team 控制 + 3 只读诊断）：
  `start_team`/`end_team`/`create_worker`/`create_workers`/`send_to_worker`/
  `switch_focus`/排队消息控制/`idle_worker`/`archive_worker` 等。
- MCP 工具与 renderer IPC **共用同一组 main 侧 service**，权限/状态/回滚语义一致：
  - `OrcaLifecycleService`（team lifecycle）
  - `OrcaWorkerCreationService`（worker 创建与校验）
  - `OrcaTeamService`（派活/resume/idle/archive/auto-bridge）
  - `OrcaInterAgentDispatcher`（Lead↔Worker 消息直发/排队/accepted callback）

#### 关键不变量

- **工具可见性不是权限边界**：`cindy_orca` 全局可见，差异由 handler + host service 拒绝。
- **Codex MCP context 路由 fail-closed**：只用 `params._meta.threadId` 路由（`mcp-session-id`
  不证明 session 归属）；缺失/未知/不一致时**不注入 context**，安全降级为 NO_SESSION_CONTEXT，
  绝不猜 ctx 造成跨会话串线。
- **worker 控制入口按 caller 自身 Lead 身份做归属校验**（`resolveWorkerRef` 同时接受
  worker_id/session_id，但只在 caller 自己的 worker 列表内解析）。
- **Orca Worker 派单不得由原生 subagent 冒充**；Lead 必须按执行通道验收并标明
  `Orca Worker` 或 `native subagent`。
- **Model 不可中途换，effort 可调**（model 切换破坏 cache 前缀稳定）。
- Worker idle release（无损 hibernate）：超空闲阈值且无运行 turn/排队输入时，CAS 原子写
  `status=idle` + `idle_since`，释放本地 runtime 但保留记录/历史/上下文。

#### 未来方向

把 Orca 泛化成「主线旁的 side activity / child execution」统一外壳：`worker` /
`side_chat`（fork 分支对话）/ `workflow_run`（确定性编排 step 树）。三态拆分：
**对象在不在**（exists/deleted）、**UI 显不显示**（active/archived）、**后台醒没醒**
（live/dormant），不再让 `idle`/`archive`/`close` 混着表达。

### 4.3 插件系统（cindy-brain / Ghost）

`.cindy` 是以 `ghost.json` 为身份卡的插件包（现行唯一形态 `kind: 'chip'`）。代码用
`cindy-brain`/`Ghost` 命名，产品对外称「插件」。规则见
`plugin-security-and-authoring.md`。

#### 运行时沙箱

- 每个运行中的插件用**独立 Electron 沙箱进程 + 专属 session partition**，禁止直接访问
  Node、宿主文件系统、网络。
- 插件只能读自身安装目录内经安全相对路径校验的静态资源。
- 逻辑页经最小 `contextBridge` 管子申请主机能力；面板 webview 零特权桥。
- 主机按 `webContents` 绑定反查真实 ghostId，**不信任 sender 自报身份**。

#### 能力 slot（权限即授权边界）

所有能力必须先在 manifest 声明 slot，注入/更新确认框逐项展示，host 代码强制授权。
**prompt 不构成安全边界**。slot 实现在 `apps/desktop/src/main/cindy-brain/*Slot.ts`：

| slot | 文件 | 能力 |
|---|---|---|
| network | `networkSlot.ts` | 白名单域名；凭证由主机保险库注入，**无明文读回** |
| notify | `notifySlot.ts` | 通知 |
| badge | `badgeSlot.ts` | 未读角标（落盘账本 `ghostUnreadStore.ts`） |
| confirm | `confirmSlot.ts` | 往返确认桥 |
| fs | `fsSlot.ts` | 文件系统（grant/deposit/ledger） |
| skill | `skillSlot.ts` | **唯一越出沙箱**的能力：技能指令由主 Agent 以用户全权限执行 |
| agent | `agentSlot.ts` | Agent 编排 |
| errand | `errandSlot.ts` | 派活取件（`agent.errand`，权限档只有 plan/acceptEdits/auto，**bypassPermissions 在协议层不存在**） |
| iosSimulator | `iosSimulatorSlot.ts` | iOS 模拟器控制 |
| cindy | `cindySlot.ts` | 宿主交互 |

`skill` 槽的安全边界是**声明一致性**（manifest 与 SKILL.md frontmatter 逐字一致，
`checkSkillMdConsistency` 裁判）+ **链接对账**（`reconcileGhostSkillLinks` 只增删落在
安装根内的 symlink/junction）。

#### 存量插件兼容（红线）

任何插件系统改动必须**向下兼容**：用户升级后什么都不做，已装/已批准/已启用的插件必须
照旧可用，**绝不允许要求重新安装、重新确认权限或重新配置**。做不到必须自带自动迁移；
迁移也做不到时必须有提示 + 一次性批量恢复入口。改到插件基座的 PR 走白名单确认门。

#### 资源交接

附件/媒体/目录/保存路径经**归属校验后的 grant/deposit/ledger** 交接，禁止把宿主绝对
路径或不必要字节暴露给沙箱。媒体字节走统一入库（`media-storage-and-protocols.md`）。
模型调用一律走 Cindy 统一通道，不允许插件自建绕过通道。

#### 渐进式发现

插件发现链（花名册注入、`ghost_list`/`ghost_info`/`ghost_call` 总机、FORGE_GUIDE 作者
契约）走渐进式发现（`docs/ghost-progressive-discovery.md`）。编写手册在
`apps/desktop/src/main/cindy-brain/forge.ts` 的 `FORGE_GUIDE`，经 `ghost_forge_guide`
工具下发。

### 4.4 device-link：跨设备远程控制

`packages/device-link`（+ `device-link-protocol`）实现同账号互联的跨设备远程控制，
**零依赖、WS 实现由 host 注入**。

- `protocol.ts`：envelope 协议。
- `allowlist.ts`：IPC 隧道 allowlist（deny-by-default，控制端本机状态不能代表被控端真相）。
- `transport.ts`：重连/心跳。
- `client.ts`：客户端。

Desktop（`apps/desktop/src/main/device-link`）作被控端时，Orca team 的 Lead/Worker/team
真身都在被控端进程内编排，控制端只按 session 来源经隧道路由。老被控端没有对应 channel
时回 `CHANNEL_NOT_ALLOWED`，控制端 **fail-closed 置灰入口**并提示设备版本过旧。

Mobile 用 device-link 发现并远程控制桌面设备、镜像会话。

### 4.5 模型桥接链路

Cindy 让 Claude Code SDK 可经网关访问非 Anthropic 后端，链路设计精巧：

- `model-providers`：模型供应商目录 + 路由抽象（Anthropic/OpenAI/XD），纯逻辑。
- `anthropic-compat-proxy`：本地回环 HTTP 代理，剥离 Anthropic 专有字段。
- `anthropic-responses-bridge`：作为 `RoutingDecision.localHandler`，进程内做
  Anthropic Messages API ↔ OpenAI Responses API 转换。
- `responses-anthropic-bridge`：反向 Responses → Anthropic Messages 桥（请求/图片/工具/
  thinking 转换 + SSE 回译）。

Codex `developerInstructions` 有两条投递通道（`cindy_gateway` 走 HTTP Responses 可改写正文；
`cindy_openai` 走 WebSocket 只做 socket 隧道），每个 thread **只选择一个**投递来源，
禁止同时走两条通道。

## 5. 工程规范与工作流

### 5.1 提交门禁（硬性）

无论 PR 还是直接 commit，提交前必须：

1. `pnpm test:unit`（全部单元测试）通过；
2. 对改动涉及的每个 package 跑 `pnpm --filter <包名> run --if-present typecheck` 通过；
3. 每个 commit 带 `Signed-off-by`（DCO）。

不得通过跳过/删除/弱化测试制造通过。高风险/基础设施改动追加 `pnpm test:all`。

### 5.2 规则文档体系

`docs/` 下分三类权威规则，**读取时机触发**——做对应类型改动前必读：

- `dev-rules/`：工程（架构不变量、Electron 安全、maker-core、Orca、插件、数据库、协议、
  日志脱敏、updater、mobile、environment-setup 等）。
- `product-rules/`：产品（core-product-principles、review-product-direction、
  region-and-editions、task-and-conversation-naming、telegram-bot-parity）。
- `design-rules/`：设计（`DESIGN.md` 为权威视觉规范正文，颜色 token、双模式交付门槛）。

`AGENTS.md`（Codex/Claude Code 共用项目指令正本，`CLAUDE.md` 只 `@AGENTS.md`）是所有
任务的入口，列出每条规则的触发条件。

### 5.3 几条贯穿性原则

- **PR-first**：代码通常从非默认分支经 PR 进 `main`；非 draft PR 触发自动 code review
  （建议性）+ client-ci 机器门禁（硬性）。
- **双模式 UI**：所有新增/修改 UI 必须同时实现 Light + Dark，颜色走语义 token，禁止硬编码。
- **术语表**：UI 产品术语必须查 `i18n/GLOSSARY.md`，已裁决照用不自造；拿不准的加
  `status: "proposed"` 讨论。门禁 `pnpm check:i18n-glossary`。
- **任务/对话/消息**：`session` 面向用户叫「任务」，「对话」只用于任务内交流过程，单条
  往来叫「消息」。
- **日志脱敏**：deny-by-default 白名单方向（不得改成黑名单），记录边界（写侧续行转义与
  读侧切分是同一条不变量的两半），脱敏规则只增不减。
- **凭证安全**：凭证/令牌/授权文件不得写入仓库或 Git 跟踪路径。

## 6. 技术亮点小结

1. **连接层哲学**：Cindy 不重造智能，而是忠实传递底层 Harness 的能力/工具/事件/上下文/
   结果，不在中间造成无意损失。maker-core 是这一哲学的代码体现。

2. **代码优先于 prompt 的确定性**：能用代码保证的（校验、状态机、流程编排、权限、重试）
   一律写进代码，prompt 只承担真正需要语言理解的部分。这避免了 LLM 行为漂移。

3. **prompt cache 前缀稳定性的工程化守护**：把 system prompt 拼接顺序、易变内容隔离、
   tool/MCP 注册时机都写成不变量，并配实测要求——这是生产级 Agent 应用的关键性能优化。

4. **多 Harness 统一抽象**：通过 BaseAgent + Translator 模式，把 Claude Code / Codex / Pi
   三套异构 Harness 收进统一 `AgentEvent` 流，同一任务可混用。

5. **Orca 多 Agent 协同的工程化**：Lead/Worker/Team 数据模型、fail-closed context 路由、
   归属校验纵深防御、auto-bridge/settle/rollback 状态机、无损 idle hibernate——把多 agent
   协同的竞态、越权、消息丢失等难题都建成了不变量。

6. **Electron 安全纵深**：Renderer 不可信 → preload 最小桥 → IPC 授权边界 → Main 特权，
   配合 sandbox/contextIsolation/CSP/Fuses/webview hardener，XSS 不能升级为系统权限。

7. **插件沙箱 + 能力 slot**：每个插件独立沙箱进程，能力显式声明 + host 强制授权，资源
   走 grant/deposit/ledger，skill 槽用声明一致性 + 链接对账作为越出沙箱的安全边界。
   存量兼容是红线。

8. **分层测试与门禁自动化**：90 个 migration、分层 test-workspaces、DCO/i18n/术语/颜色/
   端点/调度多个 guard 脚本，把规则变成可执行检查。

9. **布局树作为用户级配置**：递归 split 树 + `panelKind` 身份 + 首帧同步就位 + 位置记忆，
   避免了「先画默认再跳成用户布局」的体验缺陷，且 renderer/main 共用纯函数校验。

10. **双区域与多账号**：`cn`/`global` 区域身份、多账号数据库架构、device-link 被控端为
    真相源——产品形态的工程化落地。
